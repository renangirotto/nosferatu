---
title: BlogArticle
description: A layout that renders a whole article document from a required title and description, with the body in its default slot.
---

`BlogArticle` is a layout, not a component: it renders the entire document — doctype, `<html>`, `<head>` and `<body>` — so a page file can be nothing but the layout and its content. That is also why there is no live demo on this page: a document cannot be nested inside this one.

The document and its head are not hand-written here. The layout renders [BaseHtml](/html/base-html/) with [BaseHead](/html/base-head/) in its `head` slot, and puts its own markup in the body — see those pages for the full metadata list and for how to add a tag the head does not cover.

[See it rendered →](/examples/blog-article/)

```astro
---
import BlogArticle from 'astro-nosferatu/layouts/BlogArticle.astro';
---
```

## Usage

```astro
---
import BlogArticle from 'astro-nosferatu/layouts/BlogArticle.astro';
---

<BlogArticle
	title="Nosferatu, a sympathy for the night"
	description="A worked example of the BlogArticle layout, rendered as its own document."
>
	<p>The article body goes here, as ordinary markup or library components.</p>
</BlogArticle>
```

## Rendered markup

```html
<!doctype html>
<html lang="en">
	<head>
		<!-- everything BaseHead renders: charset, color-scheme, generator,
		     viewport, favicon, canonical, og:* and twitter:* -->
		<title>Nosferatu, a sympathy for the night</title>
		<meta name="description" content="A worked example of the BlogArticle layout, rendered as its own document." />
	</head>
	<body>
		<main class="nf-layout-blog-article">
			<article class="nf-layout-blog-article-content">
				<h1>Nosferatu, a sympathy for the night</h1>
				<p>A worked example of the BlogArticle layout, rendered as its own document.</p>
				<!-- slot content -->
			</article>
		</main>
	</body>
</html>
```

The layout writes two classes: `nf-layout-blog-article` on `main` and `nf-layout-blog-article-content` on the `article`. The `h1` and the paragraph under it are deliberately unclassed — reach them as `.nf-layout-blog-article h1` and `.nf-layout-blog-article-content > p`.

In a real build you will also see Astro's own scope on these elements (an `astro-<hash>` class or a `data-astro-cid-<hash>` attribute, depending on your `scopedStyleStrategy`). The layout declares a `<style>` block, so Astro scopes it; that marker is generated, is not part of the layout's contract, and is not something to write selectors against.

## Props

| Prop               | Type     | Required | Default | What it does                                                                                                                                       |
| ------------------ | -------- | -------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `title`            | `string` | Yes      | —       | Used twice: as the document's `<title>` and as the `h1` at the top of the article.                                                                 |
| `description`      | `string` | Yes      | —       | Used twice: as the page's `<meta name="description">` and as the paragraph directly under the heading.                                             |
| `lang`             | `string` | No       | `'en'`  | The `lang` attribute of the `<html>` element, passed through to [BaseHtml](/html/base-html/).                                                      |
| `imageSocialMedia` | `string` | No       | —       | The sharing image, passed through to [BaseHead](/html/base-head/) and rendered as `og:image` and `twitter:image`. Omit it and neither tag appears. |

`title` and `description` are required, and `astro check` reports a missing one as a type error rather than rendering an empty heading or paragraph. The layout accepts nothing else: it does not forward native attributes and does not merge a `class`, because the markup above is its contract.

## Slots

| Slot    | Required | What it renders                                                                                                                                               |
| ------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| default | No       | The article body, rendered inside the `article` immediately after the description paragraph. Omit it and the article is just the heading and the description. |

## Styling

The layout styles two things: the **width** of the article and the **font** its prose and code are set in. It sets no font size — headings and paragraphs take the library's global [type scale](/styles/#typography), the same as everywhere else on the page — and no spacing or color.

### The article's width

The `article` is centred in `main`, fills the available width, and stops growing at a cap:

```css
.nf-layout-blog-article-content {
	margin-inline: auto;
	inline-size: 100%;
	max-inline-size: var(--nf-layout-blog-article-max-inline-size, var(--nf-container-small-size));
}
```

The cap defaults to [`--nf-container-small-size`](/styles/#container), `856px`. The layout never declares `--nf-layout-blog-article-max-inline-size` itself, so you can set it on `:root`, on `.nf-layout-blog-article` or on the article, and your value wins whatever the order:

```css
/* A narrower article, without moving the shared container size */
.nf-layout-blog-article {
	--nf-layout-blog-article-max-inline-size: 640px;
}
```

### The article's fonts

| Elements                   | Property                                    | Default                                                            |
| -------------------------- | ------------------------------------------- | ------------------------------------------------------------------ |
| `p`, `strong`, `span`, `a` | `--nf-layout-blog-article-font-family`      | [`--nf-font-family-blog-post`](/styles/#fonts) — Plus Jakarta Sans |
| `p`                        | `--nf-layout-blog-article-font-weight`      | [`--nf-font-weight`](/styles/#fonts) — `400`                       |
| `code`, `pre`              | `--nf-layout-blog-article-font-family-code` | [`--nf-font-family-code-blog-post`](/styles/#fonts) — Geist Mono   |

Three details are deliberate:

- **Headings are left out.** They inherit the page's general font from `body`, so an article reads as Outfit for its structure and Plus Jakarta Sans for its prose.
- **`strong` gets the family but not the weight.** Applying `400` to it would un-bold every emphasis in the article, so it keeps the browser's own heavier weight.
- **`pre` is styled as well as `code`**, because a fenced block is `<pre><code>` and `pre` carries the browser's own monospace, which would otherwise beat inheritance.

All of this applies to the markup you pass into the default slot just as much as to the heading and description the layout renders itself — the rules are rooted at `.nf-layout-blog-article`, and the body of an article _is_ slot content. Nothing outside that root is touched.

As everywhere else in the library, the fonts are **named, not loaded**: install the [Fontsource packages](/styles/#opting-in) to get them, or let each stack fall through to a system font.

```css
/* A serif article on an otherwise sans-serif site */
.nf-layout-blog-article {
	--nf-layout-blog-article-font-family: 'Lora Variable', Georgia, serif;
}
```

### Every property the layout exposes

| Property                                    | Default                                                       | What it controls                       |
| ------------------------------------------- | ------------------------------------------------------------- | -------------------------------------- |
| `--nf-layout-blog-article-max-inline-size`  | not declared — falls back to `var(--nf-container-small-size)` | Maximum width of the `article`.        |
| `--nf-layout-blog-article-font-family`      | `var(--nf-font-family-blog-post)`                             | Font of `p`, `strong`, `span` and `a`. |
| `--nf-layout-blog-article-font-family-code` | `var(--nf-font-family-code-blog-post)`                        | Font of `code` and `pre`.              |
| `--nf-layout-blog-article-font-weight`      | `var(--nf-font-weight)`                                       | Weight of the article's paragraphs.    |

### Everything else

`.nf-layout-blog-article` is the hook for everything the layout leaves alone:

```css
.nf-layout-blog-article {
	padding: 2rem 1rem;
}

.nf-layout-blog-article h1 {
	text-wrap: balance;
}
```

Everything the library's **stylesheets** ship sits in the `nosferatu` cascade layer, so your unlayered rules beat them outright. The layout's own rules are a scoped `<style>` block rather than a layer: Astro compiles them to a single class plus an element (`.nf-layout-blog-article p`), the lowest specificity that can do the job, so your rule matches it exactly and wins on order. If you would rather not depend on order at all, set the custom properties above instead of overriding the rules.

:::caution[The layout no longer has its own type scale]
Earlier versions sized `h1`–`h4` and `p` from a separate fluid scale. It is gone: these properties no longer have any effect, so remove any override of them — `--nf-layout-blog-article-viewport-min`, `-viewport-max`, `-viewport-progress`, `-font-size-base`, `-type-scale-min`, `-type-scale-max`, `-type-scale`, `-font-size-h1`, `-font-size-h2`, `-font-size-h3`, `-font-size-h4` and `-font-size-p`.

Text in the article now follows the global [`--nf-typography-*`](/styles/#typography) scale, so headings render slightly larger than before. The global scale does not size `h4`, so an `h4` in an article now has the browser's default size. If the article should differ from the rest of the page, write an unlayered rule scoped to it, such as `.nf-layout-blog-article h4 { font-size: 1.5rem; }`.
:::
