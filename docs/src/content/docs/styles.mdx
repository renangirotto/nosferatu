## Import everything

Load `index.css` once, for example in your base layout:

```astro
---
import 'astro-nosferatu/styles/index.css';
---
```

It includes, in order:

| File                      | What it contains                                                                                                                                              |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `tokens.css`              | Every token the library publishes, as four imports — it declares nothing itself                                                                               |
| `colors/index.css`        | The color palette, which is a folder: it imports the two files below and declares nothing itself                                                              |
| `colors/colors-dark.css`  | Every `-d-` token on `:root` — the dark-mode scale, opaque and 25% opacity                                                                                    |
| `colors/colors-light.css` | Every `-l-` token on `:root` — the light-mode scale, opaque and 25% opacity                                                                                   |
| `shadows.css`             | `--nf-shadow-*` box-shadow values on `:root`, one per palette color, plus `--nf-shadow-depth`                                                                 |
| `spacings.css`            | `--nf-spacing-*` on `:root` — the spacing scale, in `px`                                                                                                      |
| `borders.css`             | `--nf-border-radius-*` on `:root` — the corner radii, in `px`                                                                                                 |
| `reset.css`               | box-sizing, margin reset, `color-scheme`, `100dvh` body container, media and form-control defaults, text wrapping                                             |
| `typography.css`          | `--nf-typography-*` and `--nf-font-*` custom properties on `:root`, a fluid `font-size` on `h1`, `h2`, `h3` and `p`, and the font family and weight of `body` |

`tokens.css` is the aggregate: importing it is the same as importing `colors/index.css`, `shadows.css`, `spacings.css` and `borders.css`, and it declares no property of its own. The typographic properties are **not** part of it — `--nf-font-family`, `--nf-font-weight` and the `--nf-typography-*` scale come with `typography.css`, which also owns the element rules that use them.

`typography.css` is the only file besides the reset that touches your own elements: loading `index.css` sizes your `h1`, `h2`, `h3` and `p`, and sets the font family and weight of your `body`, which everything else inherits. It sizes nothing else — `a`, `h4`–`h6`, lists, blockquotes and code keep the browser's own sizes — and it sets no color, line-height or margin on anything. See [Typography](#typography) for the full property list, [Fonts](#fonts) for the three typefaces, and both for how to opt out.

## Cascade layers

`index.css` declares three cascade layers:

```css
@layer nosferatu.tokens, nosferatu.reset, nosferatu.typography;
```

```
nosferatu.tokens < nosferatu.reset < nosferatu.typography < your unlayered CSS
```

The palette and the shadows sit inside `nosferatu.tokens`: they arrive through `tokens.css`, which `index.css` imports into that one layer. There is no `nosferatu.colors` and no `nosferatu.shadows` — if you want your own overrides inside the library's layer order rather than unlayered, `@layer nosferatu.tokens { … }` is the layer to target.

Any CSS you write outside a layer wins over the library, whatever its specificity. No `!important` needed:

```css
/* your stylesheet, loaded after index.css */
h1 {
	color: rebeccapurple;
}
```

The tokens are layered too, so an unlayered `:root { --nf-… }` override wins whether it loads before or after `index.css`.

## Import single files

Each file can be imported on its own, for example to keep your own reset:

```astro
---
import 'astro-nosferatu/styles/tokens.css';
import 'astro-nosferatu/styles/typography.css';
---
```

Or take one token group and leave the rest — `tokens.css` is a convenience, and each group it imports stands on its own:

```astro
---
import 'astro-nosferatu/styles/colors/index.css';
import 'astro-nosferatu/styles/shadows.css';
import 'astro-nosferatu/styles/spacings.css';
import 'astro-nosferatu/styles/borders.css';
---
```

The palette is split by scale, so you can take one and leave the other — useful if your project pins a single `color-scheme`:

```astro
---
import 'astro-nosferatu/styles/colors/colors-light.css';
---
```

`colors/index.css` is exactly those two imports and nothing else, so loading it is the same as loading both.

:::caution
Files imported on their own are **not** layered. Only `index.css` adds the `nosferatu.*` layers.
:::

:::note[Moved in this release]
The palette used to be a single file at `astro-nosferatu/styles/colors.css`. That path no longer resolves — replace it with:

```astro
import 'astro-nosferatu/styles/colors/index.css';
```

No token was renamed or revalued, so nothing else in your CSS changes. If you load `astro-nosferatu/styles/index.css`, there is nothing to do.
:::

:::note[Renamed and removed in this release]
`tokens.css` no longer declares anything itself, and the spacing, radius and font ladders it used to hold are gone. Rename what you use:

| Removed            | Was       | Use instead                     | Value  |
| ------------------ | --------- | ------------------------------- | ------ |
| `--nf-space-1`     | `0.25rem` | `--nf-spacing-base-low-3`       | `4px`  |
| `--nf-space-2`     | `0.5rem`  | `--nf-spacing-base-low-2`       | `8px`  |
| `--nf-space-3`     | `0.75rem` | `--nf-spacing-base-low-1`       | `12px` |
| `--nf-space-4`     | `1rem`    | `--nf-spacing-base`             | `16px` |
| `--nf-space-6`     | `1.5rem`  | `--nf-spacing-base-up-2`        | `24px` |
| `--nf-space-8`     | `2rem`    | `--nf-spacing-base-up-4`        | `32px` |
| `--nf-radius-sm`   | `0.25rem` | `--nf-border-radius-base-low-1` | `4px`  |
| `--nf-radius-md`   | `0.5rem`  | `--nf-border-radius-base`       | `8px`  |
| `--nf-radius-full` | `9999px`  | nothing — write the value       | —      |

The new values are `px` where the old ones were `rem`. They are the same size at the default root font size and differ if you changed it; override a step to get a scaling value back.

The font tokens are gone too. `--nf-font-body` and `--nf-font-heading` were `--nf-font-family` with a fallback, and `--nf-font-mono` was `--nf-font-family-code-blog-post` with one — use those two properties, which come from `typography.css` and are still [the single place to substitute a font](#fonts). The rest have no replacement; write the value they held:

- `--nf-font-size-sm`, `-md`, `-lg`, `-xl`, `-2xl`, `-3xl` → `0.875rem`, `1rem`, `1.25rem`, `1.5rem`, `2rem`, `2.5rem`, or the fluid [`--nf-typography-font-size-*`](#typography) properties for document text
- `--nf-font-weight-normal`, `-medium`, `-bold` → `400`, `500`, `700`
- `--nf-line-height-body`, `--nf-line-height-heading` → `1.6`, `1.2`

Finally, the `nosferatu.colors` and `nosferatu.shadows` layers no longer exist. If you wrote `@layer nosferatu.colors { … }`, target `@layer nosferatu.tokens` instead — that is now the one layer holding every token.
:::

## Tokens

Every value the library uses is a custom property prefixed with `--nf-`, and every one of them is grouped in the stylesheet that defines it:

| Group         | File               | Tokens                                                                                                          |
| ------------- | ------------------ | --------------------------------------------------------------------------------------------------------------- |
| Spacing       | `spacings.css`     | `--nf-spacing-*`, [below](#spacing)                                                                             |
| Border radius | `borders.css`      | `--nf-border-radius-*`, [below](#border-radius)                                                                 |
| Color         | `colors/index.css` | `--nf-<hue>-<d\|l>-<step>`, see [Colors](#colors)                                                               |
| Shadow        | `shadows.css`      | `--nf-shadow-*`, see [Shadows](#shadows)                                                                        |
| Typography    | `typography.css`   | `--nf-font-family*`, `--nf-font-weight`, `--nf-typography-*`, see [Typography](#typography) and [Fonts](#fonts) |

### Spacing

Space between and inside elements — `margin`, `padding`, `gap` and the like. The scale is named by distance from a `16px` base:

| Token                     | Value  |
| ------------------------- | ------ |
| `--nf-spacing-none`       | `0px`  |
| `--nf-spacing-base-low-4` | `2px`  |
| `--nf-spacing-base-low-3` | `4px`  |
| `--nf-spacing-base-low-2` | `8px`  |
| `--nf-spacing-base-low-1` | `12px` |
| `--nf-spacing-base`       | `16px` |
| `--nf-spacing-base-up-1`  | `20px` |
| `--nf-spacing-base-up-2`  | `24px` |
| `--nf-spacing-base-up-3`  | `28px` |
| `--nf-spacing-base-up-4`  | `32px` |

### Border radius

Corner radii, and nothing else: the library publishes no token for a border's width, style or color.

| Token                           | Value  |
| ------------------------------- | ------ |
| `--nf-border-radius-base-low-1` | `4px`  |
| `--nf-border-radius-base`       | `8px`  |
| `--nf-border-radius-base-up-1`  | `12px` |

Both scales are absolute `px`, not `rem`. They are geometry, so they stay put when a reader — or your own CSS — changes the root font size; only type scales with it. Override a step on `:root` in unlayered CSS if you want different spacing, including a value that does scale:

```css
:root {
	--nf-spacing-base: 1.25rem;
}
```

## Colors

`colors/` holds the color palette, split into `colors-dark.css` and `colors-light.css`. There are no semantic color tokens: styles and components use palette steps directly.

Each token is named `--nf-<hue>-<scale>-<step>`:

- **hue**: `blue`, `cyan`, `green`, `grey`, `orange`, `pink`, `purple`, `red`, `yellow`
- **scale**: `d` for dark mode, `l` for light mode
- **step**: `10` to `100`, in tens; `grey` also has `110` to `200`

For example `--nf-red-l-80` or `--nf-blue-d-20`. All values are OKLCH.

Every one of those tokens has a translucent sibling with the same color at 25% alpha, named with a `-25` suffix: `--nf-red-l-80-25`, `--nf-blue-d-20-25`. Use them for tinted surfaces and hairlines that should let the page show through — that is how `Callout` draws its panel and its separator rule. The values are written out literally, so they need no `color-mix()` or relative-color support:

```css
:root {
	--nf-purple-l-40: oklch(0.76 0.13 301.9);
	--nf-purple-l-40-25: oklch(0.76 0.13 301.9 / 25%);
}
```

The library styles currently use the light (`-l-`) scale:

| Role                    | Token                                                                |
| ----------------------- | -------------------------------------------------------------------- |
| Headings, body copy     | inherited from the page — the library sets no `body` color           |
| Muted text (`small`)    | `--nf-blue-l-80`                                                     |
| Surface (`code`, `pre`) | `--nf-blue-l-10`                                                     |
| Links                   | `--nf-red-l-80` (hover `--nf-red-l-90`)                              |
| Components              | their own `--nf-<component>-*` properties, resolved from the palette |

### Grey

`grey` is the palette's neutral. It is a hue like the other eight — same `--nf-grey-<scale>-<step>` naming, same 25% tier, same shadow tokens — not a semantic "surface" or "muted" alias. There is no `--nf-neutral-*` or `--nf-surface-*`; if you want a neutral, you pick a grey step the same way you pick a blue one.

Both scales are bounded by the same two anchors: `#f9f9f9` at the light end and `#282A36` at the dark end. They traverse that range differently. `grey-d` is the dark-mode scale, so it spends its first half near white, where a dark-mode surface lives, then falls away faster. `grey-l` is evenly spaced across the whole range, because a light-mode neutral is used for text and rules more often than for surfaces.

The hue angle is `277.5` on every step — the cast measured off `#282A36`. Chroma climbs from `0` to `0.02` with the step, so the pale greys are exactly neutral and only the dark end carries a trace of blue.

Below `#282A36`, both scales continue with ten near-black steps, `110` to `200`. These steps are the same on both scales. Lightness drops by an even `0.02` per step, down to `0.09` at `200`, which is still distinguishable from pure black. Chroma eases back to `0.01`, so the darkest greys stay neutral instead of turning blue. Use them for deep dark-mode surfaces under `grey-d-100`. They have the same 25% tier and shadow tokens as every other step.

:::note[`grey-d-100` and `grey-l-100` are the same color]
Both scales end on `#282A36`, so those two tokens resolve identically. Every other hue has a distinct `d-100` and `l-100`. That falls out of the greyscale being bounded by two fixed anchors rather than being an oversight — but it does mean `light-dark(var(--nf-grey-l-100), var(--nf-grey-d-100))` will not change between schemes. The same holds for every step from `110` to `200`, which the two scales share.
:::

## Shadows

`shadows.css` turns the library's one house shadow — a solid `0px 4px 0px` offset, the raised look `Button` and `Callout` share — into a token per palette color:

```astro
---
import 'astro-nosferatu/styles/shadows.css';
---
```

Each token is named `--nf-shadow-<hue>-<scale>-<step>` and holds the **complete** `box-shadow` value for the palette color of the same name, so you apply it in one declaration:

```css
.card {
	box-shadow: var(--nf-shadow-purple-l-80);
}
```

<div class="not-content demo">
	<div class="demo-card" style="box-shadow: var(--nf-shadow-purple-l-80); background-color: var(--nf-purple-l-40-25);">box-shadow: var(--nf-shadow-purple-l-80)</div>
	<div class="demo-card" style="box-shadow: var(--nf-shadow-green-l-80); background-color: var(--nf-green-l-40-25);">box-shadow: var(--nf-shadow-green-l-80)</div>
</div>

A shadow token resolves the palette token it names, so overriding `--nf-purple-l-80` moves both the color and its shadow. The tokens exist only for the opaque palette — there is no `-25` shadow — and `shadows.css` needs the palette loaded to resolve.

One more token holds the offsets on their own:

```css
.card {
	box-shadow: var(--nf-shadow-depth) var(--my-accent);
}
```

Use `--nf-shadow-depth` when the shadow's color is decided somewhere else — in particular when it has to follow the color scheme. `light-dark()` resolves _colors_, not whole values, so it cannot pick between two complete shadow tokens; it can pick the color you hand to `--nf-shadow-depth`. That is exactly how `Callout` draws its shadow.

:::note
These are plain custom properties, not a function: the color is baked into the name. When CSS custom functions are available everywhere, this file collapses into one function without changing a single call site.
:::

## Typography

`typography.css` sizes `h1`, `h2`, `h3` and `p` with a type scale that interpolates with the viewport, so text grows as the window widens instead of stepping at breakpoints:

```astro
---
import 'astro-nosferatu/styles/typography.css';
---
```

It is the one library stylesheet besides the reset that styles your own markup. On those four elements it sets `font-size` and nothing else — no color, line-height or margin — and it additionally sets the font family and weight of `body`, which is covered under [Fonts](#fonts) below. `a` is deliberately left out of the scale, so a link inside a heading renders at the heading's size instead of shrinking to body size. `h4`, `h5` and `h6` are left alone too.

[**See it live →**](/examples/typography/) — a standalone page that loads the library's styles and nothing else, reporting the viewport width, each element's computed size as you resize, and the computed font of `body`.

### Properties

Every input is a custom property on `:root`, so you retune the scale by overriding one:

| Property                            | Default                            |
| ----------------------------------- | ---------------------------------- |
| `--nf-typography-viewport-min`      | `560px`                            |
| `--nf-typography-viewport-max`      | `1088px`                           |
| `--nf-typography-viewport-progress` | `progress(100svw, …-min, …-max)`   |
| `--nf-typography-font-size-h1-min`  | `3rem`                             |
| `--nf-typography-font-size-h1-max`  | `3.5rem`                           |
| `--nf-typography-font-size-h1`      | interpolated between the two above |
| `--nf-typography-font-size-h2-min`  | `2.5rem`                           |
| `--nf-typography-font-size-h2-max`  | `3rem`                             |
| `--nf-typography-font-size-h2`      | interpolated between the two above |
| `--nf-typography-font-size-h3-min`  | `2rem`                             |
| `--nf-typography-font-size-h3-max`  | `2.5rem`                           |
| `--nf-typography-font-size-h3`      | interpolated between the two above |
| `--nf-typography-font-size-p-min`   | `1rem`                             |
| `--nf-typography-font-size-p-max`   | `1.125rem`                         |
| `--nf-typography-font-size-p`       | interpolated between the two above |

```css
/* your stylesheet, unlayered */
:root {
	--nf-typography-font-size-h1-max: 5rem;
	--nf-typography-viewport-max: 1440px;
}
```

An unlayered rule beats the library's layer whatever its specificity, so you never need `!important` — you can also just size an element yourself:

```css
h1 {
	font-size: 2rem;
}
```

### The bounds are real limits

Each element reaches its minimum at `--nf-typography-viewport-min` and its maximum at `--nf-typography-viewport-max`, and **holds** there outside that range — `progress()` clamps its own result to `0`–`1`, so the library wraps it in nothing:

| Viewport | `h1`            | `p`               |
| -------- | --------------- | ----------------- |
| `320px`  | 48px (`3rem`)   | 16px (`1rem`)     |
| `560px`  | 48px (`3rem`)   | 16px (`1rem`)     |
| `800px`  | 51.64px         | 16.91px           |
| `1088px` | 56px (`3.5rem`) | 18px (`1.125rem`) |
| `2560px` | 56px (`3.5rem`) | 18px (`1.125rem`) |

To opt one element out of the scale entirely, set its resolved property to a constant. It then renders at that size at every width, inside the range as well as outside:

```css
:root {
	--nf-typography-font-size-p: 1.125rem;
}
```

### Opting out completely

`typography.css` only arrives with `index.css`, and it carries both the type scale and the [font properties](#fonts). Import the other two files individually to get everything else and keep your own text styling:

```astro
---
import 'astro-nosferatu/styles/tokens.css';
import 'astro-nosferatu/styles/reset.css';
---
```

Remember that files imported on their own are **not** layered, so your own CSS no longer automatically wins over the reset.

:::caution[The scale is progressive enhancement]
It relies on the CSS [`progress()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/progress) function. The element rules sit behind an `@supports` check, so a browser without `progress()` keeps its own heading and paragraph sizes with the hierarchy intact — rather than collapsing every heading to body size, which is what would happen unguarded. Do not depend on an exact rendered size.
:::

:::note[Why the headings on this page are not fluid]
These docs are a Starlight site, and Starlight declares its own cascade layers _after_ importing the library. Later-declared layers win, so Starlight's heading rules outrank `nosferatu.typography` here — only the paragraphs on this page are sized by the scale. That is ordinary layer precedence rather than a defect, and it is why the demo lives on [its own page](/examples/typography/). The same happens in your project if you declare layers after loading `index.css`.
:::

## Fonts

The library uses three typefaces, each with a job:

| Property                          | Default                                                                                                       | Where it applies                                                           |
| --------------------------------- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| `--nf-font-family`                | `'Outfit Variable', 'Outfit', system-ui, -apple-system, 'Segoe UI', Roboto, sans-serif`                       | `body` — the whole page, by inheritance                                    |
| `--nf-font-family-blog-post`      | `'Plus Jakarta Sans Variable', 'Plus Jakarta Sans', system-ui, -apple-system, 'Segoe UI', Roboto, sans-serif` | `p`, `strong`, `span` and `a` inside [BlogArticle](/layouts/blog-article/) |
| `--nf-font-family-code-blog-post` | `'Geist Mono Variable', 'Geist Mono', ui-monospace, 'SF Mono', Menlo, Consolas, monospace`                    | `code` and `pre` inside [BlogArticle](/layouts/blog-article/)              |
| `--nf-font-weight`                | `400`                                                                                                         | `body`, and `BlogArticle`'s paragraphs                                     |

All four are declared on `:root` by `typography.css`.

:::caution[The library names these fonts. It does not load them.]
No font file ships in the package, there is no `@font-face` rule anywhere in it, and nothing is ever requested from a font host. **Install nothing and every stack falls through to the system font it ends with** — the same rendering you had before, with no failed request.
:::

### Opting in

Install the families you want — they are optional peer dependencies, so your package manager never pulls them in by itself — and import them in your project:

```sh
npm install @fontsource-variable/outfit @fontsource-variable/plus-jakarta-sans @fontsource-variable/geist-mono
```

```astro
---
import '@fontsource-variable/outfit';
import '@fontsource-variable/plus-jakarta-sans';
import '@fontsource-variable/geist-mono';
import 'astro-nosferatu/styles/index.css';
---
```

Each stack names the variable family first and the static one second, so `@fontsource/outfit` works just as well as `@fontsource-variable/outfit`; the variable build wins when both are installed. This site does exactly the above, which is why you are reading it in Outfit and its code samples in Geist Mono.

### Using your own font

Override the property in unlayered CSS — there is no element rule to rewrite:

```css
/* your stylesheet, unlayered */
:root {
	--nf-font-family: 'Inter Variable', system-ui, sans-serif;
}
```

`--nf-font-family` is the only property for the page's general text: `body` takes it, everything inside inherits it, and the library's own components read it directly, so one override moves all three.

To keep the library's sizing but none of its fonts, set the three family properties to your own stacks. To drop both, import `tokens.css` and `reset.css` individually instead of `index.css`, as under [Opting out completely](#opting-out-completely) — the font properties arrive with `typography.css`.

## Theming

Override tokens after loading the styles to re-theme the library, including components:

```css
:root {
	--nf-red-l-80: var(--nf-purple-l-80);
	--nf-red-l-90: var(--nf-purple-l-90);
	--nf-font-family: 'Inter', sans-serif;
	--nf-spacing-base: 20px;
}
```

You can also scope an override to part of a page:

```css
.promo {
	--nf-red-l-80: var(--nf-green-l-80);
}
```
