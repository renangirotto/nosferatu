## Import everything

Load `index.css` once, for example in your base layout:

```astro
---
import 'astro-nosferatu/styles/index.css';
---
```

It includes, in order:

| File | What it contains |
|---|---|
| `tokens.css` | `--nf-*` custom properties on `:root` (spacing, fonts, radius) |
| `colors.css` | `--nf-*` color palette on `:root` (light and dark scales, opaque and 25% opacity) |
| `shadows.css` | `--nf-shadow-*` box-shadow values on `:root`, one per palette color, plus `--nf-shadow-depth` |
| `reset.css` | box-sizing, margin reset, `color-scheme`, `100dvh` body container, media and form-control defaults, text wrapping |

The library styles no headings, paragraphs, lists, links or code: text on your page keeps the browser's own sizes, weights and margins, except where the reset changes them.

## Cascade layers

`index.css` puts every file in its own cascade layer:

```css
@layer nosferatu.tokens, nosferatu.colors, nosferatu.shadows, nosferatu.reset;
```

```
nosferatu.tokens < nosferatu.colors < nosferatu.shadows < nosferatu.reset < your unlayered CSS
```

Any CSS you write outside a layer wins over the library, whatever its specificity. No `!important` needed:

```css
/* your stylesheet, loaded after index.css */
h1 {
	color: rebeccapurple;
}
```

Tokens and colors are layered too, so an unlayered `:root { --nf-… }` override wins whether it loads before or after `index.css`.

## Import single files

Each file can be imported on its own, for example to keep your own reset:

```astro
---
import 'astro-nosferatu/styles/tokens.css';
import 'astro-nosferatu/styles/colors.css';
import 'astro-nosferatu/styles/shadows.css';
---
```

:::caution
Files imported on their own are **not** layered. Only `index.css` adds the `nosferatu.*` layers.
:::

## Tokens

Every value the library uses is a custom property prefixed with `--nf-`:

| Group | Tokens |
|---|---|
| Spacing | `--nf-space-1` (0.25rem), `--nf-space-2`, `--nf-space-3`, `--nf-space-4`, `--nf-space-6`, `--nf-space-8` (2rem) |
| Font family | `--nf-font-body`, `--nf-font-heading`, `--nf-font-mono` |
| Font size | `--nf-font-size-sm`, `-md`, `-lg`, `-xl`, `-2xl`, `-3xl` |
| Font weight | `--nf-font-weight-normal`, `-medium`, `-bold` |
| Line height | `--nf-line-height-body`, `--nf-line-height-heading` |
| Radius | `--nf-radius-sm`, `--nf-radius-md`, `--nf-radius-full` |

## Colors

`colors.css` holds the color palette. There are no semantic color tokens: styles and components use palette steps directly.

Each token is named `--nf-<hue>-<scale>-<step>`:

- **hue**: `blue`, `cyan`, `green`, `orange`, `pink`, `purple`, `red`, `yellow`
- **scale**: `d` for dark mode, `l` for light mode
- **step**: `10` to `100`, in tens

For example `--nf-red-l-80` or `--nf-blue-d-20`. All values are OKLCH.

Every one of those tokens has a translucent sibling with the same color at 25% alpha, named with a `-25` suffix: `--nf-red-l-80-25`, `--nf-blue-d-20-25`. Use them for tinted surfaces and hairlines that should let the page show through — that is how `Callout` draws its panel and its separator rule. The values are written out literally, so they need no `color-mix()` or relative-color support:

```css
:root {
	--nf-purple-l-40: oklch(0.76 0.13 301.9);
	--nf-purple-l-40-25: oklch(0.76 0.13 301.9 / 25%);
}
```

The library styles currently use the light (`-l-`) scale:

| Role | Token |
|---|---|
| Headings, body copy | inherited from the page — the library sets no `body` color |
| Muted text (`small`) | `--nf-blue-l-80` |
| Surface (`code`, `pre`) | `--nf-blue-l-10` |
| Links | `--nf-red-l-80` (hover `--nf-red-l-90`) |
| Components | their own `--nf-<component>-*` properties, resolved from the palette |

## Shadows

`shadows.css` turns the library's one house shadow — a solid `0px 4px 0px` offset, the raised look `Button` and `Callout` share — into a token per palette color:

```astro
---
import 'astro-nosferatu/styles/shadows.css';
---
```

Each token is named `--nf-shadow-<hue>-<scale>-<step>` and holds the **complete** `box-shadow` value for the palette color of the same name, so you apply it in one declaration:

```css
.card {
	box-shadow: var(--nf-shadow-purple-l-80);
}
```

<div class="not-content demo">
	<div class="demo-card" style="box-shadow: var(--nf-shadow-purple-l-80); background-color: var(--nf-purple-l-40-25);">box-shadow: var(--nf-shadow-purple-l-80)</div>
	<div class="demo-card" style="box-shadow: var(--nf-shadow-green-l-80); background-color: var(--nf-green-l-40-25);">box-shadow: var(--nf-shadow-green-l-80)</div>
</div>

A shadow token resolves the palette token it names, so overriding `--nf-purple-l-80` moves both the color and its shadow. The tokens exist only for the opaque palette — there is no `-25` shadow — and `shadows.css` needs `colors.css` loaded to resolve.

One more token holds the offsets on their own:

```css
.card {
	box-shadow: var(--nf-shadow-depth) var(--my-accent);
}
```

Use `--nf-shadow-depth` when the shadow's color is decided somewhere else — in particular when it has to follow the color scheme. `light-dark()` resolves *colors*, not whole values, so it cannot pick between two complete shadow tokens; it can pick the color you hand to `--nf-shadow-depth`. That is exactly how `Callout` draws its shadow.

:::note
These are plain custom properties, not a function: the color is baked into the name. When CSS custom functions are available everywhere, this file collapses into one function without changing a single call site.
:::

## Theming

Override tokens after loading the styles to re-theme the library, including components:

```css
:root {
	--nf-red-l-80: var(--nf-purple-l-80);
	--nf-red-l-90: var(--nf-purple-l-90);
	--nf-font-body: 'Inter', sans-serif;
}
```

You can also scope an override to part of a page:

```css
.promo {
	--nf-red-l-80: var(--nf-green-l-80);
}
```
